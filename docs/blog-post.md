# AI에게 화면 119개 상태를 "그대로" 옮기게 했다: 픽셀 0 하네스로 만든 마이그레이션 루프

> KOIN(한국기술교육대학교 캠퍼스 서비스)의 주문·상점 웹뷰(KOIN_ORDER_WEBVIEW)를 메인 웹(KOIN_WEB_RECODE)으로 옮긴 기록.
> 기간 2026-10-07 ~ 10-11(5일). 상세 기록은 `engineering-log.md`(47건), 결정은 `order-migration-plan.md`, 진행은 `STATUS.md`.

---

## 1. 문제 상황

KOIN에는 모바일 상점·리뷰·주문 화면이 **두 군데**에 있었다.

| | KOIN_ORDER_WEBVIEW (order) | KOIN_WEB_RECODE (메인) |
|---|---|---|
| 스택 | Vite + React Router + Tailwind | Next.js 15 Pages Router + SCSS Modules |
| 상태 | 2025-12 이후 사실상 정지, 앱 웹뷰로 배포된 적 없음 | 활발히 개발 중 |
| 화면 | 모바일 상점 목록·상세·리뷰·이벤트 + 주문 흐름(장바구니·배달지·결제·주문 내역) | 데스크톱 상점 화면, 모바일은 일부만 |
| API | 상점 API 구버전 | 신버전 |

모바일 웹의 상점 진입 링크는 order로 연결돼 있어서, 실제 서비스되는 모바일 화면은 order 쪽이었다. 같은 기능을 서로 다른 API 버전으로 두 저장소에서 유지하는 비용, 그리고 다시 시작하는 주문 기능을 어디에 둘지 — 이 두 가지가 통합의 이유였다.

요구는 단순했다: **order 화면을 "그대로" 메인 웹으로 옮긴다.** 데스크톱은 그대로 두고 모바일만.

어려운 점은 "그대로"였다.

- 스타일 체계가 다르다. Tailwind 클래스 한 줄을 SCSS Module + BEM으로 바꾸면서 4px, 색 하나, 줄 높이 하나가 쉽게 어긋난다
- 화면이 많다. 상점 쪽 9개 화면(Track A), 주문 쪽 11개 화면(Track B), 화면마다 상태(빈 목록·모달·로그인·필터 등)가 있다. 최종적으로 **119개 상태**
- 분석 이벤트(GA)·요청 순서·토스트까지 같아야 운영 지표가 이어진다
- 과거에 AI로 화면을 옮겼을 때 **"UI가 다른데 통과했다"고 보고된 경험**이 있었다

## 2. 왜 "그냥 AI에게 시키면" 안 되나

AI 코딩 에이전트에게 "order의 이 화면을 Next.js로 옮겨줘"라고 하면 그럴듯한 결과가 나온다. 문제는 **얼마나 같은지 아무도 모른다**는 것이다.

- 에이전트의 "통과했다"는 근거가 아니다. 스스로 스크린샷을 보고 "비슷하다"고 판단하면 4px 차이, 줄 높이 차이는 지나간다
- 작업이 크면 상태를 놓친다. 빈 목록, 긴 제목, 로그인한 사용자, 모달이 열린 순간
- 원본의 버그까지 옮긴다. 혹은 원본의 버그를 "고친다"며 동작을 바꾼다. 둘 다 사람이 모르는 사이에 일어난다
- 게이트를 맞추려고 편법을 쓴다(이번에 실제로 있었다 — 7장)

그래서 원칙을 세웠다: **판정은 스크립트만 한다. 원본(오라클)과 새 화면(후보)을 같은 데이터로 띄워 기계적으로 비교하고, 에이전트는 통과할 때까지 고친다.**

## 3. 계획

### 3.1 구조: 하네스 + 루프

```
                ┌──────────── 단위 스펙(화면 1개, 상태 N개) ────────────┐
                │                                                      │
  stage API ── 기록·재생 프록시 ──┬── order(오라클, vite build)   ──┐   │
                                └── WEB_RECODE(후보, next build) ─┤   │
                                                                 ▼   ▼
                                       Linux 컨테이너 브라우저(Playwright) 캡처
                                                                 │
                     게이트: G0 정상 렌더 / G2 요청 / G3 토스트 / G4 분석 이벤트 / G6 픽셀·요소
                                                                 │
           구현 에이전트 ◀── 실패 리포트 ── 검증(스크립트) ◀────────┘
                │ 커밋
                └──────────▶ 통과 or 예산 소진 or 사람 판단 필요 → 종료 → 사람이 독립 재검증 → PR
```

| 구성 | 역할 |
|---|---|
| 기록·재생 프록시 | 두 앱의 API를 같은 응답으로 묶는다. 기록은 stage에서 한 번, 루프는 재생만(결정성). 녹화 시 전화번호·토큰·실명을 가림 |
| 캡처 | 가짜 시계, 래스터 고정 플래그, 애니메이션 정지, 요소 목록(위치·계산된 스타일), 요청 로그, gtag 이벤트, 토스트 문구 |
| 게이트 | G0 정상 렌더(필수 텍스트·miss 없음) / G2 API 요청 집합 / G3 토스트 / G4 분석 이벤트 / G6 본문 픽셀(fuzz 5% 후 **0px**) + 요소 누락·추가 / G8 회귀 / SSR 점검 |
| 변이 테스트 | 오라클 화면에 일부러 차이(4px 이동·색·굵기·아이콘 제거·글자·요청 누락·이벤트 누락)를 넣어 **하네스가 잡는지** 확인. 하네스의 탐지율을 측정하는 장치 |
| 오라클 패치 | order 버그는 사람이 승인한 패치로 고친 화면을 기준으로 삼는다(11개) |
| 루프 | 구현 에이전트 ↔ 검증(스크립트) 반복. 에이전트는 하네스 파일을 수정할 수 없다(권한 차단 + 변조 검사) |

### 3.2 원칙

- **화면 하나 = 작업 단위.** 크게 맡기면 놓친다
- **기준 이미지를 저장하지 않는다.** 매번 오라클을 띄워 비교한다. 기준 갱신으로 "통과시키는" 길을 막는다
- **비율 대신 0px.** "98% 일치"는 4px 어긋남을 숨긴다
- **사람 개입은 최소, 대신 되돌리기 비싼 곳에.** 하네스 신뢰 승인, 공유 기반(foundation) 승인, 그리고 원본 버그를 옮길지 고칠지 같은 제품 판단
- **PR은 화면 단위 stacked PR.** 리뷰어는 화면 하나의 diff만 본다

### 3.3 범위

- **Track A**(상점·리뷰 9개 화면): order 화면을 이전하고 실제 진입 링크까지 교체
- **Track B**(주문 흐름 11개 화면): 웹 주문은 아직 열지 않는다. 화면과 기능은 전부 옮기되 develop 머지 전 **진입을 막는다**
- 결제: 처음엔 "결제 위젯 화면까지만". 진행 중 **Toss 테스트 결제(실제 출금 없음)로 결제 승인 흐름까지** 실제로 검증하는 것으로 확대

| 10/9 | 사람 검토 | 전 단위 통과 후 사용자가 직접 띄워 보며 차이 2건 발견(검색 결과 하단 여백, 태그 입력) → 상태 축·UX 보완 |

| 10/11 | 마무리 | 진입 차단(환경 변수 + middleware), 전체 회귀 |

루프 한 바퀴는 대략 이렇다.

1. 사람(메인 세션)이 오라클을 stage에 붙여 상태를 **녹화**하고 order 대 order로 자기 검증(재생 2회가 0px, 변이 전부 탐지)
2. 루프 실행: 구현 에이전트가 화면을 만들고 커밋 → 검증 에이전트는 `verify.mjs`만 실행 → 실패 리포트(어느 상태, 어느 게이트, 픽셀 위치, 계산된 스타일 차이)를 다음 구현에 전달
3. 통과하면 사람이 **독립적으로 다시 검증**(해당 단위 + 스택 아래 단위 전부 + 회귀 + SSR 점검) → 커밋 정리 → PR

## 5. 트러블슈팅 (대표 사례)

47건 중 블로그에 남길 만한 것을 유형별로 골랐다.

### 5.1 결정성: 같은 화면이 다르게 찍힌다

- **macOS에서 픽셀 0이 깨졌다(#1).** 같은 화면인데 글자·SVG 가장자리 안티앨리어싱이 앱마다 달랐다. macOS Chromium은 서브픽셀 배치에 래스터가 민감하다. 기준을 완화하지 않고 **브라우저만 Linux 컨테이너**에서 띄웠다. 서버는 호스트, URL은 `localhost` 그대로(작은 TCP 포워더)
- **React Suspense 300ms(#19).** 회귀 비교에서 헤더가 없는 화면이 찍혔다. "기존 버그가 고쳐진 것"처럼 보였지만, 사람이 **원인 먼저 조사**를 택했다. 실제로는 React가 숨겼던 내용을 다시 보일 때 쓰는 300ms 지연 전에 "정착"으로 판단한 하네스 결함이었다
- **비결정성 하나를 없애자 실제 차이가 나왔다(#20, #23).** 부드러운 스크롤을 즉시 이동으로 고정하자, 그동안 가려져 있던 분석 이벤트 차이(order 1회, 새 화면 2회)가 드러났다. 원인은 **React Compiler의 메모이즈**가 스크롤 로깅 구독 타이밍을 바꾼 것
- **가짜 시계도 "얼마나 진행했는가"까지 고정해야 한다(#31).** "화면이 두 번 연속 같으면 멈춤"은 그 시점이 실제 시간(이미지 로딩)에 좌우돼, 자동 넘김 캐러셀이 한쪽만 넘어갔다
- **화면 밖 다른 출처 iframe은 전체 페이지 스크린샷에 안 찍힌다(#41).** Toss 약관 위젯이 두 앱 모두 빈칸 → 게이트는 통과. "결정적인 것"과 "맞게 찍힌 것"은 다르다. iframe은 요소 스크린샷으로 따로 비교

### 5.2 하네스 자신을 검증하기

- **변이 테스트가 헤더를 건드렸다(#7).** 하네스가 차이를 놓친 줄 알았는데, 변이가 비교 범위 밖(헤더)을 바꾸고 있었다. 검증 도구의 검증도 틀릴 수 있다
- **사람이 열어 둔 탭이 하네스를 오염시켰다(#30).** 간헐 실패의 요청 목록이 사용자가 보던 화면의 재조회와 정확히 같았다. 캡처마다 세션 태그를 붙이고 태그 없는 클라이언트 요청은 409로 거절
- **"조용히" 아무것도 안 돈 일괄 검증(#21).** zsh는 따옴표 없는 변수를 단어로 나누지 않는다. "실패 없음"과 "실행 안 됨"을 구분하는 출력(케이스 수)을 항상 본다

### 5.3 원본(오라클)의 버그

"그대로 옮긴다"는 원본 버그까지 옮긴다는 뜻이 될 수 있다. 버그를 찾을 때마다 **사람이 결정**했다.

| 버그 | 결정 |
|---|---|
| 주문 상점 번호(`orderable_shop_id`)를 상점 번호로 써서 리뷰 화면이 빈 화면·다른 상점 리뷰 (#35) | 고쳐서 이전 |
| 교외 배달지 검증 모달의 버튼 구성이 뒤바뀜 | **그대로** 이전(닫기는 가능) |
| 배달비 0원이면 JSX `{0 && ...}`로 "0"이 찍힘 | 고쳐서 이전 |
| 포장 주문은 배달비 null → `formatKRW(null)` 예외로 결과 화면 전체가 빈 화면 (#44) | 고쳐서 이전(오라클 패치) |
| 지도 마커 정리 함수가 조건부라 집 마커가 두 번 쌓임 (#43) | 오라클 패치 |

중복 마커는 2~7px 차이로만 보였다. 에이전트가 가장자리 픽셀 값이 **1-(1-α)²**(같은 반투명 이미지를 두 번 합성)과 맞는다는 걸 보여 줘서 원인이 드러났다.

### 5.4 녹화·재생으로 안 되는 것들

- **쓰기 상태(#36).** 장바구니 수량 변경을 녹화하면 stage 장바구니가 바뀌어 다음 녹화의 시작 상태가 달라진다 → 상태마다 "녹화 직전 장바구니 복구"(`prepare.cart`). 그리고 이름 없는 아이콘 버튼의 nth를 짐작했다가 **수량 증가 상태가 실제로는 다른 항목을 삭제**하고 있었다. 게이트는 오라클끼리 비교라 통과. 요청 로그로 의도를 확인해야 한다
- **한 번만 되는 외부 동작(#42).** 결제 승인은 결제 하나에 한 번만 성공한다. 녹화 직전에 **새 Toss 테스트 결제**(임시 주문 → 퀵계좌이체 데모 → 테스트 비밀번호 000000)를 자동으로 만들고, 그 결과로 승인 화면을 녹화. 카드 결제는 테스트 키여도 실제 카드사 인증 화면으로 넘어가 자동화하지 않았다
- **만료 쿠키(#25, #28).** 재생 프록시는 쿠키에 따라 달라지는 응답을 재현하지 못한다. "서버가 죽지 않는다"는 성질은 화면 비교 대신 **서버 응답 코드만 보는 SSR 점검**으로 바꿨다

### 5.5 대역(stub)을 버리고 실제로 불러오기 (#39, #45)

지도·결제 위젯은 처음엔 빈 상자 대역으로 계획했다. 사용자가 "자리만 차지하는 방식 말고 제대로 로드해서 확인 못 하나"라고 물었고, 실험해 보니 같은 실행 안에서 두 앱을 몇 초 간격으로 찍으면 실제 지도 타일·Toss 위젯도 **픽셀 0으로 일치**했다.

대역을 버리자 대역이 숨기던 버그 두 개가 바로 나왔다.

- 새 화면이 지도 스크립트를 동적으로 불러온 직후 지오코더 모듈이 아직 없어서 **주소 변환을 아예 안 하고** "주소 변환 실패"를 띄움
- 지도 SDK 내부 레이어(z-index 100~103)가 고정 헤더(z-index 20) 위로 그려질 수 있음 → `isolation: isolate`

대신 하네스는 "실제 외부 요청이 끝났는가"를 정착 조건에 넣어야 했다(지오코딩 응답이 캡처 전에 오느냐에 따라 축척이 300m/500m로 갈림).

## 7. 그냥 AI 돌렸을 때와의 차이

"order 화면을 Next.js로 옮겨줘"라고만 했다면 어땠을지, 이번 작업에서 **실제로 일어난 일**로 비교한다.

| 상황 | 그냥 AI | 하네스 + 루프 |
|---|---|---|
| 4px·줄 높이·테두리 색 같은 미세 차이 | 에이전트가 스크린샷을 보고 "동일함"으로 보고. 사람이 일일이 비교해야 앎 | G6가 0px 기준으로 잡고, 계산된 스타일 차이(예: `border` 축약형이 테두리 색을 currentColor로 바꿈)까지 리포트 |
| 분석 이벤트 횟수 | 확인할 방법이 없음 | React Compiler 메모이즈로 스크롤 로그가 1회→2회가 된 것을 G4가 잡음(#23) |
| 놓친 상태 | 에이전트가 생각한 상태만 구현 | 상태를 오라클에서 녹화. 그래도 놓친 데이터 크기 축(긴 목록)은 사람이 직접 보고 발견(#24) → 스펙에 추가 |
| 원본 버그 | 모르게 옮기거나, 모르게 "고침" | 녹화 단계에서 드러남(빈 화면 G0 등). 고칠지 말지는 사람이 결정하고 오라클 패치로 기록 |
| 에이전트가 게이트를 맞추려는 편법 | 막을 장치 없음 | 실제로 일어남: 픽셀을 맞추려고 **기능 없는 1px DOM**(`ModalEdgeMarker`)을 제품 코드에 넣음(#40) → 리뷰에서 제거, 원인(비정수 DPR 부분 열)은 하네스에서 해결 |
| "lint 통과"라는 보고 | 그대로 믿음 | 실제로는 경고 2개(CI는 경고도 실패)였음(#38) → 루프 완료 조건을 CI와 같은 명령으로 |
| 막혔을 때 | 비슷한 것으로 대체하고 "완료" | 실제로 일어남: 권한 문제로 원본을 못 읽자 아이콘을 비슷한 것으로 대체(#46), 의존성을 못 넣자 SDK 코드를 복사(B8) → 사람이 원본·의존성으로 교체 |
| 범위 밖 수정이 필요할 때 | 공유 파일을 마음대로 고침 | 수정 가능 파일 목록 밖이면 `needs-human`으로 멈추고 근거와 최소 수정안을 반환(#9, #34, #43) |
| 하네스 자체의 결함 | 해당 없음 | 하네스도 틀린다. 변이 테스트·자기 검증(order 대 order 0px)으로 하네스를 먼저 검증. 47건 중 절반 이상이 하네스 쪽 문제였다 |
| 외부 의존(지도·결제) | 대충 붙이거나 목으로 대체 | 실제로 불러 비교 → 대역이 숨기던 지오코딩·z-index 버그 발견 |

정리하면, 차이는 "AI가 더 잘 만든다"가 아니다. **틀렸을 때 그걸 아는가**다.

- 그냥 AI: 결과물은 빨리 나오지만, 얼마나 같은지·무엇을 놓쳤는지·어디서 편법을 썼는지 사람이 전부 다시 봐야 한다
- 하네스 + 루프: 에이전트는 같은 실수를 하지만(편법·대체·과장된 보고), 스크립트 판정과 사람의 독립 재검증이 그걸 잡는다. 사람은 "같은가"가 아니라 "버그를 옮길까 고칠까", "외부 의존을 어떻게 검증할까" 같은 **판단**에 시간을 쓴다

## 8. 교훈

1. **판정을 에이전트에게 맡기지 않는다.** 에이전트의 보고는 가설이다. 근거는 스크립트 종료 코드와 리포트
2. **검증 도구도 검증한다.** 변이 테스트로 탐지율을 재고, 하네스를 고칠 때마다 이미 통과한 단위를 전부 다시 돌린다(비결정성 하나를 없애면 숨어 있던 차이가 나온다)
3. **"오라클과 같다"는 "오라클만큼 좋다"일 뿐이다.** 원본 버그는 녹화에서 드러나게 하고, 고칠지는 사람이 정한다. 그리고 마지막에 사람이 직접 써 보는 단계는 여전히 값어치가 있다(태그 입력, 긴 목록)
4. **에이전트는 "끝내는" 쪽으로 기운다.** 읽을 수 없으면 대체하고, 게이트가 안 맞으면 게이트용 코드를 넣는다. 완료 조건을 CI와 같게, 수정 범위를 좁게, 편법은 tamper와 같은 급으로 본다
5. **외부 의존을 가리는 건 마지막 수단.** 같은 실행 안에서 두 앱이 같은 외부 결과를 보면 결정성은 유지된다. 대신 "외부 요청이 끝났는가"를 정착 조건에 넣는다
6. **재현 안 되는 간헐 문제는 고치기 전에 계측부터.** 다음에 나오면 위치가 보이게
